# 예시

처음 쓸 때, 또는 지도나 걷기의 형태가 헷갈릴 때 읽는다. 두 예시 모두 꾸며 낸 것이다. **형태만 참고하고, 예시에 나온 가정이나 결론을 실제 대상에 가져오지 않는다.** deep 모드의 같은 예시는 `assets/example.json`, `assets/example-report.json`에 있다.

지도에서는 "코드에서 확인 / 원문에서 확인"을 생략하고, 그보다 약한 표시(원문이 주장, 추정, 미확인)와 "실행해서 확인"만 붙인다. 걷기에서는 주장마다 붙인다 (SKILL.md 0절).

## 코드: 지도

사용자: AI가 만든 쿠폰 기능 브랜치를 머지해도 될지 판단하려 한다.

```
대상: feature/coupon 브랜치, main 대비 파일 24개 (코드 약 340줄, 테스트 약 400줄, 이름 변경 약 800줄, package-lock.json 약 300줄)

**한 줄 요지** 결제 단계에 쿠폰 적용이 추가됐고, 요청하지 않은 환불 계산 변경과 이름 변경이 섞여 있습니다.

**당신이 할 일** 1번(요청에 없던 환불 변경)을 받아들일지 결정, 2번의 DB 마이그레이션이 코드보다 먼저 적용되는지 확인. 3·4번은 grasp의 판단이니 "틀렸다면 드러날 곳"을 직접 보세요.

**미확인** 테스트를 실행하지 않아 통과 여부는 모릅니다. 쿠폰 예약의 고유 키가 운영 DB에 적용됐는지 모릅니다. 하위 의존성 변경의 영향은 확인하지 않았습니다.

**얕게 읽은 것** `package-lock.json` 변경(약 300줄)은 버전 숫자만 훑어봤습니다. `package.json`의 직접 의존성은 바뀌지 않았습니다.

**그림**
장바구니
  → [2 🔴] 쿠폰 검증과 예약 (신규, DB 변경)
  → 금액 계산
      ├→ 결제
      └→ [1 🔴] 환불 계산 (변경됨)

**구성**
1. 🔴 환불 금액 계산 변경 (약 40줄, 요청에 없음) — 쿠폰 주문의 환불 계산식이 바뀜.
2. 🔴 쿠폰 검증과 예약 (약 300줄) — 요청한 핵심 로직이지만, 동시 사용 방지가 이 브랜치의 DB 마이그레이션(고유 키)에 기댐. 되돌리기 어려운 변경.
3. 🟡 테스트 (약 400줄) — 적용 경로만 검증, 환불 경로 테스트는 없음. 틀렸다면 드러날 곳: `src/coupon/apply.test.ts:40` (중복 사용 거절을 단언한다고 읽었음. 호출만 한다면 🔴)
4. ⚪ 이름 변경 (약 800줄, 요청에 없음) — grasp 판단: 건너뛰어도 됨. `src/checkout` 안에서만 쓰는 `OrderForm` → `CheckoutForm`, diff 전체를 읽었고 밖에서 쓰는 이름은 바뀌지 않음. 틀렸다면 드러날 곳: `src/checkout/service.ts:88` (이름 외의 토큰이 바뀐 줄이 가장 많은 곳). 기계적 확인은 아래 명령 (모두 출력이 없어야 함)

**새 용어** `CouponLedger`: 쿠폰 사용 예약과 기록을 남기는 테이블.

1번부터 볼까요?
```

지도가 길어지지 않도록 기계적 확인 명령은 지도 아래에 따로 붙인다. 앞의 셋은 이름 변경만 있는지, 뒤의 셋은 grasp가 주장한 범위(`src/checkout`)가 맞는지 본다. 범위 안으로만 제한한 확인은 그 범위가 틀렸다는 것을 잡지 못하기 때문이다.

```bash
git diff --word-diff=porcelain --word-diff-regex='[A-Za-z0-9_]+|[^[:space:]]' main...feature/coupon -- src/checkout | grep -E '^[-+]' | grep -vE '^(---|\+\+\+) ' | grep -vxE -e '-OrderForm' -e '\+CheckoutForm'
git diff main...feature/coupon -- src/checkout | grep -E '^[-+](.*["'"'"'](OrderForm|CheckoutForm)["'"'"']|[[:space:]]*export[[:space:]].*(OrderForm|CheckoutForm))'
git diff --numstat main...feature/coupon -- src/checkout | grep '^-'
git grep -n -w CheckoutForm main -- src                                                     # 새 이름이 원래 있던 이름과 겹치는지
git grep -n -w OrderForm feature/coupon -- src                                              # 옛 이름이 남은 곳 (범위 밖에서 쓰던 곳 포함)
git diff main...feature/coupon -- . ':(exclude)src/checkout' | grep -E '^[-+].*(OrderForm|CheckoutForm)'   # 범위 밖에서 바뀐 곳
```

## 코드: 1번 걷기

```
**1. 🔴 환불 금액 계산 변경**

**핵심** 전에는 고객이 실제로 낸 금액(`paidAmount`)을 그대로 돌려줬습니다. `paidAmount`는 이미 할인을 뺀 결제액인데, 이제는 거기서 쿠폰 할인분을 한 번 더 뺍니다 (코드에서 확인). 요청서에는 환불 이야기가 없었습니다 (원문에서 확인).

**구체적인 예** 환불액은 `정가 − 2 × 할인분`이 됩니다 (코드에서 확인).
쿠폰 없음:   결제 10,000 → 환불 10,000
쿠폰 2,000:  결제 8,000 → 환불  6,000
쿠폰 5,000:  결제 5,000 → 환불      0
쿠폰 6,000:  결제 4,000 → 환불 −2,000

**볼 곳**
- `src/refund/calc.ts:43` — 할인분을 빼는 줄.
- `src/refund/calc.ts:43 @main` — 바뀌기 전 줄. `paidAmount`를 그대로 돌려줬다.
- `src/checkout/total.ts:22` — `paidAmount`를 계산하는 줄. 할인을 이미 뺀 금액임을 확인할 수 있다.

**주의**
- 고객에게 덜 환불되는 방향입니다. (코드에서 확인)
- 사실이라면: 의도한 정책인지 작성자에게 확인하고, 아니면 43행을 되돌려야 합니다. (추정)
- 할인분이 정가의 절반을 넘으면 환불액이 음수가 됩니다. (코드에서 확인)
- 음수 환불을 결제사로 보내기 전에 막는 곳이 있는지 확인하지 못했습니다. (미확인)

**확인** 가정: 결제 시스템이 `paidAmount`에 할인 전 금액(10,000)을 저장하고, 2천 원 할인은 결제 뒤 포인트로 돌려준다면, 바뀐 43행이 계산하는 환불액은 고객이 실제로 부담한 금액과 같아지나요?
```

## 리포트: 지도

사용자: AI가 쓴 "API 캐시 계층 도입 검토 리포트"(612줄)를 읽고 Redis 캐시 도입 여부를 정하려 한다. 앞서 "운영 인력을 따로 늘려야 한다면 도입하지 않는다, p95가 30% 이상 줄어야 한다"는 기준을 말했다.

```
대상: cache-review.md 612줄 (2026-10-28 작성, 초안). 결론·권고 약 60줄 / 벤치마크 약 180줄 / 무효화 설계 약 140줄 / 비용 약 70줄 / 캐시 일반론 약 160줄

**한 줄 요지** 리포트는 Redis 캐시 도입을 권고합니다. 핵심 수치(p95 40% 감소)는 적중률 85%를 가정한 합성 부하에서 나왔고 (원문이 주장), 권고한 무효화 방식(TTL 60초)대로면 가격이 최대 60초 낡을 수 있습니다 (추정).

**당신이 할 일** 도입 여부 결정. 1~3번이 판단 기준이고, 3번은 당신이 말한 인력 조건입니다.

**미확인** 실제 트래픽에서의 적중률과 지연. 운영 인력이 더 필요한지 (리포트는 근거 한 문장으로 0원 가정). 리포트의 벤치마크는 다시 돌려 보지 않았습니다.

**구성**
1. 🔴 지연이 정말 그만큼 줄어드나 (원문 약 180줄) — 40%는 적중률 85% 가정 위의 합성 부하 결과 (원문이 주장).
2. 🔴 데이터가 얼마나 낡을 수 있나 (원문 약 140줄) — 권고안(TTL 60초)대로면 최대 60초 (추정). 즉시 삭제 방식은 비용 수치 없이 기각됨.
3. 🔴 운영 인력이 더 드나 (원문 약 70줄) — 당신의 조건에 걸림. 리포트는 인력 비용을 근거 한 문장으로 0원으로 둠.
4. ⚪ 캐시 일반론과 벤더 소개 (원문 약 160줄) — grasp 판단: 건너뛰어도 됨. 이 서비스에 대한 측정이나 결론이 없음을 끝까지 읽고 확인함. 틀렸다면 드러날 곳: 96-118행 (이 절에서 유일하게 수치가 나오는 곳).

1번부터 볼까요?
```

덩어리들이 서로 독립된 질문이라 그림 줄은 뺐다.

## 리포트: 1번 걷기

```
**1. 🔴 지연이 정말 그만큼 줄어드나**

**핵심** 리포트는 Redis 캐시를 붙이면 주문 API의 p95 지연이 180ms에서 108ms로, 약 40% 줄어든다고 결론 내립니다 (원문이 주장). 이 수치가 도입 권고의 유일한 성능 근거입니다 (원문에서 확인).

**근거와 조건**
- 측정: 스테이징에서 상품 1,000개를 무작위로 조회하는 합성 부하, 200 rps, 10분 (원문이 주장). 측정 날짜와 버전은 적혀 있지 않습니다 (원문에서 확인).
- 적중률 85%는 측정이 아니라 가정입니다. 리포트 안에 근거가 없습니다 (원문에서 확인).
- 실제 트래픽에서 잰 도입 전후 p95는 리포트에 없습니다 (원문에서 확인).

**볼 곳**
- 212-240행 — 측정 조건과 적중률 가정.
- 251-258행 — p95 결과 표.

**주의**
- 40%는 실제 트래픽에서 잰 값이 아니므로, 지연 기준(30%)을 넘는지는 이 리포트로 판단할 수 없습니다. (추정)
- 사실이라면: 도입을 정하기 전에 실제 트래픽에서 도입 전후 p95를 재 봐야 합니다. (추정)

**확인** 가정: 리포트가 같은 합성 부하에서 적중률을 50%로 가정해 다시 잰 결과(p95 20% 감소)도 실었다면, 당신의 지연 기준(30%)에 대해 이 리포트로 말할 수 있는 것은 무엇인가요?
```
