# deep 모드

목표는 **토큰과 시간을 아끼지 않고 이해를 최대로 만드는 것**이다. 채팅만으로는 그림과 표, 주석 달린 코드, 전후 비교를 한 화면에 함께 보여 주기 어렵다. 그래서 deep 모드는 **브라우저로 여는 설명 페이지**를 만든다.

## 흐름 한눈에 보기

1. 대상을 넓게 읽는다 (1절).
2. **리포트만**: 분석 내용을 아무것도 보여 주지 않은 채 열린 기준 질문 하나만 묻고, 답이나 "건너뛰기"를 기다린다 (3절). 사용자가 이미 대화에서 기준을 말했으면 이 단계를 건너뛴다. 기준에 따라 덩어리와 등급이 바뀌므로 JSON보다 먼저 묻는다.
3. 페이지 데이터를 JSON으로 쓰고 빌드해서 검증한다 (2, 4절). 아직 열지 않는다.
4. **페이지를 열기 전에** 채팅에서 남은 질문(코드는 🔴 덩어리의 기대 질문, 리포트는 구체적인 기준 질문)을 한 메시지로 묻고 답이나 "건너뛰기"를 기다린다 (3절). 남은 질문이 없으면 이 단계를 건너뛴다.
5. 답을 JSON에 넣고 다시 빌드해서 연다. 페이지는 사용자의 답과 네 분석을 나란히 보여 준다.
6. 채팅은 피드백과 추가 질문을 맡는다 (5절).

## SKILL.md와의 관계

- **그대로 따른다**: 0절(읽기, 근거 수준, 문서 날짜와 상태), 1절(목적), 2절의 덩어리 나누기와 주의 등급, 3절의 네 칸(핵심, 예, 볼 곳, 주의), 4절의 질문 원칙, 쓰는 규칙, 보내기 전 점검.
- **바뀌는 것**:
  - 지도와 걷기는 채팅이 아니라 페이지에 담는다. 모든 🔴 🟡 덩어리를 담고, 사용자가 고르기를 기다리지 않는다.
  - 글자 그림 대신 2절의 그림을 쓴다. 지도의 "한 화면" 제한은 페이지에 적용하지 않지만, 덩어리 목록과 요약은 짧게 쓴다.
  - 🔴 덩어리는 질문을 두 개까지 둘 수 있다. 열기 전에 묻는 기대·기준 질문(`predict`)과 페이지의 확인 질문(`check`)이다.
  - 용어집은 8개까지 허용한다.
  - 걷기의 1-a, 1-b 나누기는 쓰지 않는다. 덩어리가 크면 그 화면의 그림과 "볼 곳"으로 범위를 좁힌다. 덩어리 번호는 1부터 빈틈없이 매긴다.

## 1. 더 넓게 읽는다

**코드일 때**

- 바뀐 코드의 **호출부와 피호출부**, 에러 경로, 관련 테스트, 설정, 연결된 이슈나 PR 설명까지 읽는다.
- **근거 수준을 올린다.** 사용자 자신의 저장소이고 테스트 명령이 분명하면 관련 테스트를 실행해서 "실행해서 확인"으로 올린다. 내려받은 남의 코드, 설치나 네트워크가 필요한 명령, 오래 걸리는 명령은 실행하지 않고 미확인으로 둔다.
- 대상이 현재 체크아웃된 상태와 다르면(지난 커밋, 다른 브랜치) JSON의 최상위 `rev`에 그 커밋을 적는다. 모든 `파일:줄`과 코드 발췌가 그 커밋 기준으로 검증된다.
- **변경 전 코드**를 가리킬 때는 그 참조나 `code` 그림에 따로 `"rev": "<커밋>~1"`을 붙인다. "전에는 이랬다"는 주장도 사용자가 직접 열어 볼 수 있고 빌드가 검증한다. 페이지에는 `파일:줄 @<커밋>~1`로 보인다.
- 대상이 HEAD가 아니면 **그 뒤의 이력**을 본다. `git log --oneline <대상>..HEAD -- <바뀐 파일>`로 이후 커밋을 보고, 핵심 줄은 내용으로 고정해서 따라간다: `git log -L :<함수 이름>:<파일> <대상>..HEAD` 또는 `git log -L '/<그 줄에만 있는 문자열>/,+5:<파일>' <대상>..HEAD`. 숫자 범위(`-L 120,130:<파일>`)는 **HEAD 기준 줄 번호**로 읽히므로, 대상 커밋의 줄 번호를 그대로 넣으면 다른 줄을 따라가거나 실패한다. 숫자를 쓰려면 `git show HEAD:<파일>`에서 번호를 다시 찾는다. 나중에 되돌려지거나 고쳐진 변경은 그 커밋을 `rev`로 붙여 `cautions`에 쓴다. 이때 줄 하나가 아니라 **바뀐 영역 전체**를 두 참조로 준다: 지워지기 전 `파일:시작-끝@<커밋>~1`과 지운 뒤 `파일:시작-끝@<커밋>`. 줄 하나짜리 칩으로는 무엇이 사라졌는지 페이지에서 확인할 수 없다.
- **그 전의 이력**도 본다. 지워지는 핵심 줄이 언제 왜 들어왔는지 `git log -S'<지워진 줄의 고유한 문자열>' --oneline -- <파일>`로 찾는다. 최근 커밋이 일부러 넣은 동작(테스트까지 있는 것)을 이번 변경이 뒤집으면 🔴 근거로 쓴다. 얕은 클론이면 이력이 잘려 있을 수 있으니 찾지 못한 것을 "없었다"로 쓰지 않는다.
- 커밋 메시지나 PR 설명이 다루는 범위와 실제 변경을 비교한다. 설명에 없는 변경이 있는 덩어리에는 `unrequested: true`를 붙인다.

**리포트일 때**

- 원문 전체를 읽고, 각 주장마다 **원문이 내세운 근거**(측정, 사례 증언, 논증, 전망)와 그 **조건**(환경, 기준선, 날짜나 버전)을 함께 적어 둔다.
- 원문 스스로 밝힌 한계, 반대 의견, 미해결 문제를 따로 모은다. 🔴 후보가 대부분 여기서 나온다.
- 원문에 **없는 것**도 찾되, 범위를 정확히 쓴다. "이득 수치가 없다"가 아니라 "이 문서에는 웹 서비스 처리량 비교가 없다"처럼. 인용만 하고 직접 싣지 않은 자료는 "원문이 주장"이다.
- 원문이 인용한 자료는 열어 보지 않아도 된다. 대신 열어 보지 않았다는 것을 `not_read`에 적는다.
- 문서의 날짜와 상태를 `doc`에 적는다. 오늘 기준으로 오래됐으면 그 뒤의 변화를 `unverified`에 넣고, 원문이 최신 기준으로 가리키는 문서가 있으면 `doc.latest`에 적는다.
- `look`에는 원문 파일의 줄 번호를 쓴다. 붙여 넣은 글처럼 파일이 없으면 먼저 임시 파일로 저장하고 `root`를 그 폴더로 둔다.

**예시를 베끼지 않는다.** `assets/example*.json`과 `references/examples.md`는 형식만 보여 준다. 거기 나온 가정(서비스 구성, 의존성, 수치)을 이번 대상에 가져오지 않는다. 사용자에 대한 가정은 대화에서 나온 것만 쓴다.

그림으로 그릴 관계(누가 누구를 부르는지, 상태가 어떻게 바뀌는지, 주장이 무엇에 기대는지)는 **직접 확인한 것만** 모은다. 그림을 다 그린 뒤 **화살표마다 코드나 원문에서 한 번 더 따라가 본다.** 반복문, 훅, 콜백을 거쳐 돌아가는 경로를 건너뛰고 바로 잇는 실수가 많다. 빌드는 화살표가 맞는지 확인하지 못한다.

## 2. 그림을 고른다

모든 그림은 **사용자가 가질 질문 하나에 답해야 한다.** 그림 제목을 그 질문으로 쓴다 ("환불액은 어떻게 계산되나", "요청 하나가 어디를 지나나"). 질문이 떠오르지 않으면 그 그림은 장식이므로 넣지 않는다.

| 이해할 것 | 쓸 그림 (`type`) |
| --- | --- |
| 요청이나 데이터가 지나가는 길, 모듈 의존 관계 | `mermaid` flowchart |
| 여러 주체가 주고받는 순서 (클라이언트, 서버, 훅) | `mermaid` sequenceDiagram |
| 하나의 대상이 거치는 상태 (주문, 연결, 재시도) | `mermaid` stateDiagram-v2 |
| 동작이나 계산식이 바뀜 | `before_after` |
| 여러 입력이 단계마다 어떤 값이 되는지 | `trace` |
| 사람이 직접 읽어야 하는 핵심 줄 | `code` |
| 리포트의 주장·근거 수준·조건, 선택지 비교, 테스트 범위 | `table` |
| 시간 순서 (로드맵, 마이그레이션 단계) | `table` (시점 / 상태 / 내용) |
| 주장이 어떤 가정과 근거에 기대는지 | `mermaid` flowchart (주장 → 가정 → 근거) |
| 데이터 모델, 타입 관계 | `mermaid` classDiagram 또는 erDiagram |

조합 규칙.

- **지도의 `overview`는 필수다.** 코드는 보통 flowchart로 전체 흐름을 그리고 덩어리 번호와 등급을 노드에 표시한다. 덩어리들이 서로 관계없는 리포트는 주장 표(`table`: 주장 / 근거 수준 / 조건 / 덩어리)를 쓴다.
- **🔴 🟡 덩어리는 그림을 0~3개** 넣는다. 그림이 답할 질문이 없으면 넣지 않는다. 각 그림은 서로 다른 질문에 답한다.
- **같은 화면 안에서 한 가지 사실은 한 가지 형태로만 보여 준다.** `code`가 바뀐 줄을 보여 주면 같은 줄의 `before_after`는 넣지 않는다. `trace`가 구체적인 입력을 따라가면 `example`은 다른 경우를 쓰거나 한 줄로 줄인다. `look`은 `code` 그림에 이미 나온 줄을 다시 가리키지 않는다. `predict.answer`와 같은 내용을 그림에서 되풀이하지 않는다. 다만 비교표의 한 칸이 그 내용인 경우처럼, 빼면 표가 불완전해지는 경우는 괜찮다. 글과 그림이 서로 보완하는 것은 괜찮다.
- `trace`에는 **대조 사례**를 함께 넣는다. 영향을 받지 않는 경우와 경계 경우를 열로 나란히 놓는다 (예: 쿠폰 없는 주문 / 쿠폰 주문 / 쿠폰이 결제액보다 큰 주문).
- `caption`에는 **그림만 봐서는 놓칠 한 가지**를 쓴다. 그림을 다시 말로 설명하지 않는다. Mermaid 노드 ID(`A`, `B`)는 화면에 보이지 않으므로 캡션에서는 라벨이나 색 이름으로 가리킨다.
- 그림의 내용이 모두 같은 근거 수준이면 그림에 `evidence`를 붙인다. 예: 변경 전 값을 diff에서 읽어 만든 `trace`는 `"evidence": "read"`. 칸마다 수준이 다르면 그 칸에 "(추정)"처럼 적는다.
- 그림 제목은 질문 형태로 쓴다 ("어느 줄이 바뀌었나"). 빌드가 질문이 아닌 제목을 경고한다.

### Mermaid 쓰는 법

본문 폭은 약 860px다. 이보다 넓은 그림은 75%까지만 줄어들고 그 뒤로는 가로 스크롤이 생긴다. 빌드가 너무 넓은 그림을 경고하고, 그린 그림의 폭을 알려 준다.

- 라벨 안에 **백틱(`)과 `#`, `;`를 쓰지 않는다.** `this.#options`는 `this.options (private)`처럼 풀어 쓴다.
- **flowchart와 state 라벨**은 항상 큰따옴표로 감싼다: `A["환불 계산 (변경됨)"]`.
- **sequenceDiagram**은 따옴표를 쓰지 않는다: `participant User as 고객`, `User->>API: 상품 조회 (5초)`. 따옴표를 쓰면 글자 그대로 보인다.
- 노드 등급 표시(flowchart): `:::red`(빨강 테두리), `:::yellow`(노랑), `:::gray`(회색 점선), 새로 생긴 것은 `:::new`(파랑). 캡션에서 색을 말할 때는 이 이름을 쓴다.
- 노드는 **15개 이하**, 한 노드의 가지와 **가장 넓은 층의 노드는 4개 이하**로 둔다. 넘으면 바뀌지 않은 부분을 하나로 묶거나 그림을 둘로 나눈다. 지도의 `overview`는 덩어리 목록 위에 놓이므로 더 짧게, **위에서 아래로 6~7단 이하**로 그린다 (빌드는 650px보다 높으면 경고한다). 높이를 줄일 때는 방향을 LR로 바꾸기 전에 라벨을 줄이거나 바뀌지 않은 단계를 묶는다.
- 색은 노드에만 칠할 수 있다. **화살표 하나만 바뀌었으면** 그 화살표 라벨에 "(바뀜)"이나 "(새로)"를 붙이고, 바뀌지 않은 노드를 새것처럼 칠하지 않는다.
- `flowchart TD`가 기본이다. 가지가 많은 그림은 `flowchart LR`이 더 좁게 나오기도 한다. 빌드 결과의 폭을 보고 고른다.
- 판단 분기는 마름모(`{}`) 대신 직사각형과 라벨 붙은 화살표로 그린다. 두 가지의 라벨이 엇갈려 보이면 왼쪽에 둘 가지를 먼저 선언하거나 한쪽에만 라벨을 붙인다.
- 가지 없이 한 줄로 이어지는 단계가 5개를 넘으면 세로 flowchart로 그리지 않는다. `flowchart LR`로 묶거나 번호 붙은 `table`(단계 / 무엇이 일어나나)로 쓴다. 세로로 길기만 하고 전하는 것은 순서 하나뿐이다.
- 시점이 다른 단계를 한 노드에 섞지 않는다. 예: 인스턴스를 만들 때(`ky.create`) 일어나는 일과 요청마다 일어나는 일은 따로 그린다.
- HTML 태그는 지워진다. 줄바꿈 대신 짧은 라벨을 쓴다.

## 3. 질문을 고른다

질문은 사용자의 시간을 쓴다. 근거와 한계는 `evidence.md`의 "확인 질문"과 "AI의 설명과 분류를 그대로 믿지 않게 한다"에 있다.

### 열기 전에 묻는 질문 (`predict`)

🔴 덩어리마다 하나까지 둔다. 리포트에서 처음에 묻는 열린 기준 질문("이것만은 안 되면...")은 덩어리 하나에 속하지 않으므로 이 개수에 세지 않는다. 그 질문과 답은 가장 관련 있는 🔴 덩어리의 `predict`에 넣고 (그 덩어리에는 다른 예측 질문을 두지 않는다. 덩어리마다 `predict`는 하나다), 다른 덩어리에 걸리는 기준은 그 덩어리를 🔴로 올려 반영한다. 열린 기준 질문을 뺀 나머지는 **페이지를 열기 전에 채팅에서 한 메시지로** 묻는다 (흐름 4단계). 사용자가 네 분석을 하나도 보지 않은 상태에서 자기 생각을 정해야 효과가 있다. 페이지 안에서 물으면 지도와 제목, 주의 사항에서 답이 새어 나간다.

- **코드**: 사용자의 **기대**를 묻는다. "이 경우 어떻게 동작해야 하나요?" 구현을 본 적 없는 사람에게 구현을 맞히게 하지 않는다. 커밋이나 PR 제목이 이미 말해 주는 것은 묻지 않고, 제목이 말하지 않는 결과를 묻는다.
- **설명에 없던 변경**(`unrequested`)도 사용자가 원하는 동작을 알고 있으면 그대로 기대를 묻는다 (아래 "좋음"의 환불 질문이 그렇다). 사용자가 그 기능 자체를 모를 때만 기대 대신 **기준**을 묻는다. "버그 수정 릴리스에서 기존 입력이 오류로 바뀌어도 되는 조건은 무엇인가요?"
- 아래 "나쁨" 예시가 나쁜 이유: 사용자가 원하는 동작이 아니라 **구현이 어떻게 되어 있을지**를 맞히게 하기 때문이다.
  - 나쁨: "같은 쿠폰을 두 탭에서 동시에 쓰면 어떻게 될 것 같나요?"
  - 좋음: "쿠폰을 쓴 주문을 환불하면 얼마가 돌아가야 하나요?"
- **리포트**: 사용자의 **기준**을 묻는다. 열린 질문은 JSON을 쓰기 전에, 원문을 읽은 직후 그것 하나만 따로 묻는다 (흐름 2단계). 구체적인 기준 질문은 페이지를 만든 뒤 아래 메시지로 묻는다 (흐름 4단계). 두 질문을 한 메시지에 합치지 않는다. 열린 질문으로 시작하고("이것만은 안 되면 도입하지 않겠다는 조건이 있나요?"), 그다음에 필요하면 구체적인 기준을 묻는다("지연은 얼마나 줄어야 하나요?"). 네가 분석한 차원만 물으면 사용자가 네가 생각하지 못한 기준(운영 부담 등)을 떠올리지 못한다. 정답이 있는 질문이 아니다. 사용자가 네가 생각하지 못한 기준을 말하면 **분석을 다시 한다**: 덩어리 구성, 등급, 근거, 그림, 질문을 그 기준으로 다시 본다. 그 기준에 걸리는 🟡 ⚪ 덩어리는 🔴로 올리고, `your_action`, `unverified`, `wrap_up.open`에도 넣는다. 그리고 JSON을 고친 뒤 빌드한다.
- **네 분석과 부딪칠 수 없는 질문은 내지 않는다.** 예측 질문의 가치는 사용자의 답과 네 분석이 다를 수 있다는 데 있다. 대부분이 같은 답을 하더라도("8천 원이 돌아가야 한다") 코드가 다르게 동작하면 좋은 질문이다. 반대로 "테스트는 다 통과해야 하나요?"처럼 어떤 분석 결과와도 부딪치지 않는 질문은 두지 않는다.
- 질문에 네 분석의 내용을 담지 않는다. 특히 분석 결과로 나온 수치를 질문에 넣지 않는다 (상황을 설명하는 수치는 괜찮다).

채팅에서 이렇게 묻는다.

```
페이지를 만들었습니다. 열기 전에 몇 가지만 먼저 적어 주세요. 제 분석을 보기 전에 정해 두면 판단할 지점이 바로 보입니다. 건너뛰어도 됩니다.

1. <1번 덩어리의 predict 질문>
2. <2번 덩어리의 predict 질문>
```

답이 오면 덩어리마다 `predict.user_answer`에 사용자의 말을 그대로 넣고, `predict.gap`에 그 답과 네 분석의 차이를 한 줄로 쓴다 (코드: "기대는 8천 원, grasp가 읽은 코드는 6천 원". 리포트: "인력 조건은 리포트로 판단 불가, 지연 기준은 리포트 수치가 가정 위에 있어 판단 불가"). 문서만으로 판단할 수 없으면 그렇다고 쓴다.

`predict`가 있는 덩어리의 `why`는 `predict.answer`를 되풀이하지 않는다. 페이지는 둘을 같은 화면에 보여 주므로, `why`에는 답이 말하지 않은 맥락(왜 중요한지, 어디까지 영향을 주는지)을 쓴다. 건너뛰면 `user_answer`를 비워 둔다. 그리고 다시 빌드해서 연다.

### 페이지의 확인 질문 (`check`)

🔴 덩어리에서, 틀리면 판단이 바뀔 때만 둔다. 같은 화면의 그림, 주의, 예에 이미 나온 내용으로 답할 수 없는 질문을 묻는다. **질문을 쓴 뒤 그 덩어리의 `why`, `example`, `cautions`, 캡션, 표를 다시 읽고, 답이나 `points`가 이미 거기 적혀 있지 않은지 확인한다.** 반대로 답이 페이지에 없는 코드나 일반 상식에 달려 있으면 사용자는 짐작할 수밖에 없다. 답은 **페이지에 보인 동작이나 표를 새 경우에 적용해서** 나와야 하고, 다른 코드가 필요하면 그 코드를 `code` 그림으로 보여 준다. 판단을 바꿀 위험은 언제나 그 덩어리의 `cautions`에 둔다. 확인 질문의 답이 그 위험과 겹치면 **위험을 옮기지 말고 질문을 바꾸거나 뺀다.** 표의 한 줄이 답을 말해 버리는 경우도 있다 (예: 표에 "다른 사본은 `instanceof`로만 인식"이 있으면 "재시도되나요?"의 답이 거의 나온다). 빌드는 거의 그대로 베낀 경우만 경고하고, 바꿔 말한 경우는 잡지 못한다. 페이지 내용을 새 경우에 적용하게 하는 질문이 좋다. 위험은 `cautions`에 그대로 두고, **같은 메커니즘에서 값이나 조건 하나를 바꾼 경우**를 묻는다. 그 결과가 페이지에 나열된 경우들과 달라야 한다 (예: TTL 그림이 이미 캐시에 있던 값이 낡는 경우만 보여 주면, "캐시에 없던 상품을 가격 변경 직후 처음 조회하면 무엇이 보이나"). 페이지의 공식에 숫자만 넣으면 되는 질문은 계산을 시험할 뿐이다. **새 경우는 가정임을 문장에 드러낸다** ("가정: …", "…라면"). "…라고 합니다", "…로 확인됐습니다"처럼 쓰면 사용자가 꾸며 낸 상황을 사실로 기억할 수 있다 (빌드가 이런 표현을 경고한다). "그래서 도입하겠어요?"처럼 사용자의 기준으로 결론을 내리게 하는 질문은 쓰지 않는다. 그 결론은 사용자의 몫이라 `points`로 비교할 수 없다. `points`에 답의 핵심 1~3개를 쓰면, 사용자가 답을 확인한 뒤 핵심마다 "내 답에 있음 / 없음 / 이 핵심이 틀렸다고 봄"을 고른다. 핵심 단위로 비교하는 것은 자기 채점의 과신을 줄이는 방법을 느슨하게 빌린 것이다(원래 연구의 핵심은 정답이었다). 이 핵심은 네 분석이므로 사용자가 반박할 수 있게 둔다. 예측 질문의 분석 아래에도 "확인했고 맞음 / 아직 확인 안 함 / 틀렸다고 봄"을 고르는 칸이 있고, 그 선택도 답변 복사에 들어간다.

### 모든 답에 근거를 붙인다

`predict.answer`와 `check.answer`에는 `evidence`와 `look`을 붙인다. 답의 `look`은 같은 화면의 코드 그림을 가리켜도 된다. 페이지는 답을 정답이 아니라 "grasp의 분석"으로, 근거 수준과 직접 확인할 위치와 함께 보여 준다. 사실과 판단을 섞지 않는다. 코드가 하는 일은 `answer`에(코드에서 확인), "그렇게 해야 한다" 같은 판단은 `explain`에 "(추정)"이나 "(정책 판단)"을 붙여 쓴다.

**정리(`teach_back`)는 목적에 맞을 때만** 둔다. "남에게 설명"이면 두세 문장 설명을, "승인 판단"이면 "머지할지와 그 조건"을, "의사결정"이면 "결정과 그것을 바꿀 조건"을 적게 한다.

## 4. 데이터를 쓰고 페이지를 만든다

페이지는 직접 HTML로 쓰지 않는다. **JSON 데이터만 쓰고** 스크립트가 검증해서 페이지로 만든다. 그래야 레이아웃이 매번 같고, 깨진 그림이나 틀린 줄 번호를 사용자에게 보이기 전에 잡을 수 있다.

1. JSON을 임시 파일에 쓴다. 예: `$TMPDIR/grasp-<이름>.json`. 사용자 저장소 안에는 쓰지 않는다.
2. 실행한다. 질문을 묻기 전에는 `--open` 없이, 답을 넣은 뒤에는 `--open`을 붙인다.

   ```bash
   python3 <이 스킬 폴더>/scripts/build.py <json 경로> [--open]
   ```

   Python 3.9 이상이 필요하며, Git 리비전을 참조할 때는 Git도 필요하다.

3. `ERROR`가 나오면 고치고 다시 실행한다. **통과할 때까지 사용자에게 페이지를 보이지 않는다.** `WARN`은 읽고 판단한다. 대부분의 경고는 고치는 편이 낫다.
4. 스크립트가 검사하는 것: 모든 필드의 형식, 개수, 모든 `파일:줄`이 `root`(와 `rev`) 안의 실제 파일 범위에 있는지, **`code` 발췌가 그 줄의 실제 내용과 글자 그대로 같은지**, Mermaid 문법, 그리고 헤드리스 Chrome으로 모든 그림을 실제로 그려 본 결과와 폭. 스크립트가 잡지 못하는 것은 **내용이 맞는지**다. 그림과 설명이 원문과 맞는지는 네가 확인한다.
5. Chrome이 없으면 그림 검사를 건너뛰었다는 경고가 나온다. 페이지를 여는 브라우저에서 Mermaid를 불러올 수 있으면 그림은 표시된다. 오프라인 등으로 Mermaid를 불러오지 못하면 원본 텍스트가 표시된다. 검사 여부와 실제 표시 상태를 구분해 사용자에게 알린다.
   - `page did not finish rendering in headless Chrome` 경고만으로 샌드박스 문제라고 단정하지 않는다. Chrome 오류 출력과 CDN 접근 상태를 확인한다. 샌드박스 제한이 확인되면 현재 세션의 실행·승인 정책에서 허용하는 방식으로만 재시도한다. 추가 승인이 필요하고 현재 정책에서 승인 요청을 허용할 때만 요청한다. 재시도할 수 없으면 그림을 검사하지 못했다고 알린다.
6. 출력에 "opened in the browser"가 없으면 페이지가 열리지 않은 것이다. 그때는 경로를 주고 직접 열어 달라고 한다.

### 브라우저를 열 수 없을 때

원격 접속처럼 브라우저를 열 수 없는 환경이면 페이지 경로만 알려 주고, 채팅에서 기본 모드 방식으로 진행하되 deep의 넓이를 유지한다. 질문은 똑같이 먼저 묻고, 모든 덩어리를 차례로 걷고, 그림은 글자 그림으로 그린다.

### JSON 형식

완성된 예시는 `assets/example.json`(코드)과 `assets/example-report.json`(리포트)이다. 처음 쓸 때 대상에 맞는 쪽을 한 번 읽는다. 형식만 참고한다.

```jsonc
  "wrap_up": { "remember": ["..."], "skipped": ["설명에서 뺀 것과 괜찮은 이유"], "open": ["..."] }
}
```

- 🟡 덩어리는 🔴와 같은 필드를 쓰되 `predict`는 두지 않는다. `spot_check`(틀렸다면 드러날 곳)를 붙이면 그 덩어리 화면 맨 위와 지도에 보인다.
- `predict`와 `check`에 `"repro"`로 사용자가 바로 돌려 볼 수 있는 짧은 명령(테스트 하나, REPL 한 줄)을 붙이면 "직접 돌려 보기"로 보인다. "코드에서 확인"을 몇 초 만에 사용자가 직접 확인할 수 있게 한다. 사용자 저장소에서 안전하게 돌릴 수 있는 명령만 쓴다.
- 🔴 덩어리에 `spot_check`를 붙이면 무시된다. 🔴는 "볼 곳"이 그 역할을 한다.
- **글과 표 안의 줄 참조도 검증된다.** 어떤 글 필드나 표 칸에 `source/core/Ky.ts:1337`처럼 `파일:줄`(또는 `파일:줄-줄`)을 쓰면 빌드가 `root`(와 `rev`)에서 그 줄이 있는지 확인하고, 페이지에서 "볼 곳"과 같은 클릭 가능한 칩으로 보여 준다. 빌드가 확인한 참조만 칩이 된다.
  - 파일 이름만 써도(`Ky.ts:1337`) 저장소에 그 이름이 하나뿐이면 찾아 준다. 여럿이면 전체 경로를 쓰라는 오류가 난다.
  - 기본은 최상위 `rev` 기준이다. **변경 전 코드는 `파일:줄@<커밋>`**으로 쓴다 (예: `source/core/Ky.ts:786@a0eeae2~1`). 표의 한 열이 모두 변경 전이면 표에 `"column_rev": {"1": "<커밋>~1"}`(0부터 센 열 번호)를 붙인다.
  - 확장자가 있는 파일만 인식한다. `Dockerfile`처럼 확장자가 없는 파일은 `look`에 쓴다.
  - 참조처럼 보이지만 파일이 아닌 것(`api.example.com:443`)은 경고 후 글자로 남는다. 경고를 없애려면 ``` ``api.example.com:443`` ```처럼 백틱 두 개로 감싼다.
  - 리포트는 최상위 `source_file`에 원문 파일 경로를 적으면 `212-240행` 같은 표기도 검증되고 칩이 된다. 리포트가 로컬 파일이면 `root`와 `source_file`을 **반드시** 적는다. 없으면 검증되지 않고, 본문 속 위치는 칩이 되지 않으며, 페이지 맨 위에 "참조를 저장소와 대조하지 않음"이 뜬다. (`assets/example*.json`에 `root`가 없는 것은 꾸며 낸 예시라 대조할 파일이 없기 때문이다. 실제 대상에서는 따라 하지 않는다.)
  - 칩을 누르면 빌드가 읽은 그 줄(앞뒤 2줄 포함)이 페이지 안에 바로 보인다. 지난 커밋이면 `git show` 명령도 복사할 수 있다.
  - 글 안의 참조는 **근거를 보여 주는 인용**이고, 사용자에게 읽으라고 시키는 분량은 "볼 곳"(최대 3곳)이다. SKILL.md 3절의 읽기 분량 제한은 "볼 곳"에 적용한다.
- 근거 수준 값: `run` 실행해서 확인, `read` 코드에서 확인(리포트는 "원문에서 확인"으로 표시), `claimed` 원문이 주장, `inferred` 추정, `unverified` 미확인.
- 모르는 필드는 경고와 함께 무시된다. 오타를 확인한다.

그림 형식.

```jsonc
{ "type": "mermaid", "title": "...", "source": "...", "caption": "..." }
{ "type": "before_after", "title": "...", "before": { "label": "전", "code": "..." }, "after": { "label": "후", "text": "글로 쓸 때는 text" } }
{ "type": "trace", "title": "...", "columns": ["단계", "쿠폰 없음", "쿠폰 2천 원", "쿠폰 > 결제액"], "rows": [["...", "...", "...", "..."]], "highlight_rows": [3] }
{ "type": "table", "title": "...", "columns": [...], "rows": [[...]], "highlight_rows": [] }
{ "type": "code", "title": "...", "file": "상대 경로", "start_line": 41, "code": "파일 내용 그대로", "highlight": [43], "notes": [{ "line": 43, "text": "줄 옆 주석" }] }
```

글 필드에서는 `` `코드` ``와 `**굵게**`만 쓴다. `` **`코드`** ``처럼 겹쳐도 된다. 코드 안에 백틱이 있으면 두 개로 감싼다: ``` ``The `fetch` option`` ```. `` \` ``는 이스케이프가 아니다. 다른 마크다운은 글자 그대로 보인다.

`code` 그림의 `code`는 **파일에서 그대로 복사한다.** 한 글자라도 다르면 검증에서 걸린다. 주석은 원문을 고치지 말고 `notes`에 쓴다.

## 5. 채팅에서 할 일

질문에 답을 받고 페이지를 연 뒤의 채팅은 짧게 쓴다. 열렸는지는 빌드 출력으로 확인하고 그대로 말한다.

```
설명 페이지를 열었습니다: <경로>        (열리지 않았으면: "페이지를 만들었습니다. 이 경로를 브라우저로 열어 주세요: <경로>")

**한 줄 요지** ...
**당신이 할 일** ...
**당신의 답과 다른 곳** 1번: <gap 한 줄>

1번(🔴 ...)부터 보세요. 확인 질문은 페이지에서 답하고, 다 보면 마무리 화면의 "내 답변 전부 복사"로 붙여 넣어 주세요. 중간에 궁금한 점은 여기서 물어보면 됩니다.
```

사용자가 답을 붙여 넣으면 한꺼번에 피드백한다.

- 덩어리마다 **어긋난 부분만** 구체적으로 바로잡고, 바로잡은 근거의 위치를 함께 준다. 맞은 답은 "맞습니다" 한 마디로 넘어간다.
- 사용자가 고른 표시와 실제 답이 다르면("있음"이라 했는데 답에 없거나, 그 반대) 짚어 준다.
- 사용자가 "이 핵심이 틀렸다고 봄"을 고른 핵심은 **코드나 원문을 다시 읽고 해당 줄을 인용한 뒤** 판단한다. 사용자가 맞으면 분명히 인정하고 `corrections`에 남긴 뒤 페이지를 다시 만든다. 네 분석을 유지할 때도 인용한 줄로 이유를 보여 준다.
- 사용자의 기대와 실제가 달랐던 곳은, 그 차이가 판단에 어떤 의미인지 한 줄로 짚는다. 사용자의 기대가 맞고 코드나 문서가 틀렸을 가능성도 열어 둔다.
- 마지막에 SKILL.md 5절의 세 줄 마무리를 쓴다.
- 사용자가 이어서 문답으로 확인하고 싶어 하면 `quiz-mode.md`의 "이어서 하기"를 따른다. 페이지에서 이미 답한 확인 질문은 다시 내지 않는다.

사용자가 중간에 질문하면 채팅에서 답한다. 답하면서 새 사실을 확인했거나 앞의 분석이 틀렸던 것을 알게 되면, JSON을 고치고 틀렸던 것을 `corrections`에 적어 페이지를 다시 만들고, 바뀐 점을 한 줄로 알린다. 페이지와 채팅이 서로 다른 말을 하게 두지 않는다.
